## Single-GPU partition model

The FB p32 single-GPU run has 32 logical model partitions and 1024 edge buckets.
At any training state, only 4 partitions are visible to the model because the
config has:

```text
buffer_capacity=4
```

The fast path adds hidden GPU frames:

```text
GEGE_FRAME_CACHE_HIDDEN_FRAMES=6
```

So the single-GPU partition buffer has:

```text
visible logical slots = 4
hidden physical frames = 6
total physical GPU frames = 10
```

The visible slots are the only slots used by active-edge training. Hidden frames
are staging frames. They hold future partitions that have already been copied to
GPU memory but have not yet been published into the visible state.

At reset, the frame map is:

```text
logical visible slot 0 -> physical frame 0
logical visible slot 1 -> physical frame 1
logical visible slot 2 -> physical frame 2
logical visible slot 3 -> physical frame 3
free hidden physical frames = 4, 5, 6, 7, 8, 9
```

All embedding access goes through the logical-to-physical frame map. That means
training code still addresses logical visible slots 0..3, while the buffer can
change which physical GPU frame backs a visible slot.

## Visible partitions

A state is a set of 4 resident partitions. For a state with resident partitions:

```text
[p0, p1, p2, p3]
```

the visible active edge buckets are every directed pair among those partitions:

```text
p0 -> p0, p0 -> p1, p0 -> p2, p0 -> p3
p1 -> p0, p1 -> p1, p1 -> p2, p1 -> p3
p2 -> p0, p2 -> p1, p2 -> p2, p2 -> p3
p3 -> p0, p3 -> p1, p3 -> p2, p3 -> p3
```

That is up to 16 buckets per state. Empty buckets can exist, but for FB p32 the
coverage check is based on scheduled/active bucket IDs.

For p32:

```text
bucket_id(src, dst) = src * 32 + dst
```

Diagonal buckets are the self-pairs:

```text
src == dst
bucket_id = partition * 33
```

The q4 schedule used in the 103s run has 93 states. Across those states it
covers all 1024 buckets and all 32 diagonal buckets.

## Hidden partitions

Hidden partitions are not part of the current active state. They are future
admit partitions copied into spare physical frames by the async admit preload
thread.

For transition `state_t -> state_t+1`, the scheduler determines:

```text
retained partitions = current visible partitions also present in next state
evicted partitions = current visible partitions not present in next state
admitted partitions = next visible partitions not present in current state
```

The q4 schedule is bounded by:

```text
GEGE_STATEFLOW_MAX_ADMITS=3
```

So each transition admits at most 3 new partitions. With 6 hidden frames, every
admitted partition in this schedule can be preloaded into a hidden frame before
the swap publishes it.

The validated run has:

```text
transition_admits=228
hidden_publish_parts=228
fallback_visible_admit_parts=0
```

That means every admit across the epoch was loaded through the hidden-frame
preload path, and no admit had to do a synchronous visible-slot load during the
swap.

## Single-GPU swap sequence

For each state, training happens on the current visible partitions and current
active buckets. Around the state transition, the single-GPU path does this:

1. Compute the next swap plan from current resident partitions and next resident
   partitions.
2. While training the current state, start async admit preload for the next
   transition.
3. The preload thread copies admitted partitions from host storage into pinned
   host frames, then H2D-copies them into hidden physical GPU frames.
4. At swap time, consume the finished preload result.
5. Retained partitions are kept by metadata movement in the logical-to-physical
   frame map. No D2D data copy is needed for retained partitions on the frame
   cache path.
6. Evicted visible frames are either written back immediately or marked as stale
   frames for delayed writeback.
7. Hidden preloaded frames are published by remapping the target logical visible
   slots to those hidden physical frames.
8. Old physical frames that no longer back visible slots are released to the free
   hidden-frame list after any required writeback completes.
9. Active edge buckets and mapping data are updated for the new visible state.

The important detail is that publishing a preloaded partition is a metadata
operation. The expensive H2D copy already happened in the background while the
previous state was training.

## Delayed stale writeback

When a hidden frame is published into a visible slot, the previous physical frame
for that visible slot can contain updated embeddings for an evicted partition.
Those embeddings still need to be written back to host storage.

The fast path uses delayed stale writeback:

```text
GEGE_FRAME_CACHE_DELAYED_STALE_WRITEBACK=1
```

Instead of forcing the D2H/writeback on the critical swap path, the old physical
frame is registered as stale and an async evict writeback is started. The run
should show:

```text
delayed_stale_writeback_swaps=92
```

There are 92 transitions in the q4 schedule, so this means every transition used
the delayed stale path.

If this counter is 0, swap time jumps badly. In one slow run with the same q4
state count, `swap_update_ms` was about 92.6 seconds for one epoch instead of
about 15 to 18 seconds, and the epoch time rose to about 271 seconds.

## Edge buckets during transitions

When moving to the next visible state, the graph storage keeps buckets whose
source and destination partitions are both still resident. It fetches only the
new buckets involving admitted partitions:

```text
old resident -> admitted
admitted -> new resident
```

With visible buffer size 4 and at most 3 admits, the number of new bucket pairs
per transition is bounded by:

```text
num_swap_partitions * (num_remaining_partitions + buffer_size)
```

This is why the schedule shape matters. The q4 schedule balances bucket coverage
while keeping admits bounded, so partition movement remains hidden behind
training.

## Why earlier runs got stuck around 270 to 390 seconds

The slow runs were not caused by the q4 schedule itself. They generated a
similar 93-state / 1024-bucket schedule, but they missed one or more fast paths.

Observed failure modes:

```text
Epoch about 271s:
  delayed_stale_writeback_swaps=0
  swap_update_ms about 92590
  same q4 schedule, but stale evict writeback was on the critical swap path

Epoch about 286s:
  GEGE_BOUNDED_GREEDY_COVER_REVERSE=1
  shuffle_backend=cpu
  delayed_stale_writeback_swaps=0
  swap_update_ms about 105682
  map_lookup_ms about 94809

Epoch about 392s:
  delayed stale was active
  but hidden preload was incomplete:
    partial_preload_swaps=19
    fallback_visible_admit_parts=19
    hidden_publish_parts=209 instead of 228
  map_lookup_ms was about 99479

Epoch about 391s:
  hidden_publish_parts=228 and delayed_stale_writeback_swaps=92
  but edge sampling/mapping exploded:
    edge_sample_ms about 236094
    get_edges_ms about 81076
    map_lookup_ms about 134978
```

For the 103s reproduction, check both classes of counters:

```text
swap/frame-cache:
  hidden_publish_parts=228
  fallback_visible_admit_parts=0
  preload_miss_swaps=0
  partial_preload_swaps=0
  delayed_stale_writeback_swaps=92

edge/mapping:
  shuffle_backend=gpu
  map_lookup_ms about 6500 to 7200 per epoch
  edge_sample_ms about 21000 to 25000 per epoch
```

If either group is wrong, the run is not reproducing the 103s path.
