Independent review of native CUDA P2P diagnosis, 2026-10-15

The preparation/review agent did not run GPU work. Root executed four
serialized native processes and saved native_probe_review.json plus JSONL
logs. This review independently parsed every log and rehashed the exact
source, binary, and all four logs. All hashes match the root receipt.

Result:
  Peer enabled, copy APIs: 0/32 cross-GPU cases pass; 12/12 controls pass.
  Peer disabled, copy APIs: 32/32 cross-GPU cases pass; 12/12 controls pass.
  Peer enabled, remote-read kernel: 0/2 pass; 6/6 controls pass.
  Peer enabled, remote-write kernel: 0/2 pass; 6/6 controls pass.

All expected cases completed. Every CUDA API, kernel launch, and explicit
synchronization returned success. Before each transfer, source readback and
destination sentinel initialization were exact. Source readback remained
exact after every transfer. No native case required Torch or ctypes.

Enabled copy details:
- Both directions, two repetitions, each 4 MiB / 1,048,576 uint32 values.
- All 1,048,576 destination words remained the original sentinel in every
  failing case. Both current-device choices and both source/destination
  async stream choices failed identically.
- cudaMemcpyPeer sync/async, cudaMemcpyDefault sync/async, and explicit
  cudaMemcpyDeviceToDevice sync/async all fail with peer enabled.

Kernel details:
- Both directions, each 1 MiB / 262,144 uint32 values.
- Remote-read executes on the destination GPU and reads the source GPU.
  It replaces the sentinel with wrong data: all 262,144 words mismatch.
- Remote-write executes on the source GPU and writes the destination GPU.
  All 262,144 destination words remain the sentinel.
- The same kernel's source/destination mapping follows the selected device
  correctly. This distinguishes peer memory access from the copy APIs and
  rules out a copy-engine-only explanation for these observed failures.

Interpretation:
The failure is reproducible below the training code, below Torch, with
fresh raw CUDA allocations and explicit synchronization. Enabling peer
access exposes an unusable GPU-to-GPU mapping on this host. Driver API
success and cudaDeviceCanAccessPeer capability are insufficient integrity
evidence here. The passing peer-disabled cases are compatible with the
CUDA driver's host-staged fallback; they do not establish working physical
P2P and must not be reported as direct P2P success counters.

The tests support the separate host configuration investigation (translated
IOMMU groups reported by root) but do not by themselves prove the precise
platform cause. They also cannot predict a ~100 s training epoch after a
host repair. No training run, host IOMMU setting, driver, or frozen training
artifact was changed by this probe preparation/review.
